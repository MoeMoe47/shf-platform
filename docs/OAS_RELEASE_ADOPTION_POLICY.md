# OAS release adoption policy

Proposed policy for OAS governance review. This document records required gates for a future adoption decision; it does not establish an approver, quorum, adoption or certification scheme. OAS must identify and authorize its governance decision-makers (Q10). The current repository records no approval. All dates and adoption/publication fields remain null.

## Four separate actions

1. AUTHORING: derive precise proposals from cited OAS sources; reserve stable IDs; document rationale, applicability, evidence and unresolved issues. Authoring is not approval. Current authoring source: standards/oas/authoring/first-release.json.
2. REVIEW: accept/reject/defer each proposal against its statement digest, resolve questions and domain mapping dispositions, assess the scope and completeness of the set, and approve any schema/consumer migration. Human views are generated from the authoring source. Individual review approval alone does not adopt a release.
3. ADOPTION: an explicitly authorized OAS governance action adopts exact reviewed content and release metadata. Record decision ID, adopter identity/authority reference, decision procedure/quorum reference, decision time, exact source commit, complete requirement-set checksum, approved release ID, release/effective dates and immutable approval-record reference. The approval record must be verified by the release operator through the adopted process; repository fields/digests do not authenticate an approver. Never fabricate these values.
4. PUBLICATION: after adoption and final checks, a separately authorized release operator builds from the adopted source, verifies digests, publishes an immutable artifact and generated human standard, and records publication location/time/artifact digest. Publication exposes adopted bytes; it does not create adoption or certification. Do not deploy as part of this authoring task.

## Required adoption gates

| Gate | Required evidence |
| --- | --- |
| Normative content complete | Agreed release scope, no placeholders, precise obligations/applicability, independent editorial review; Q12 explicitly resolved |
| Stable identifiers | Unique reserved IDs, canonical domain membership, duplicate-text checks, disposition of rejected IDs |
| Domain mapping reviewed | Every legacy label has approved equivalence or explicit documented non-equivalence/migration exclusion; no unresolved ambiguous label silently used |
| Open issues closed | Every release-blocking issue has a signed-off disposition; remaining deferred issues explicitly excluded from release claims |
| Requirement decisions recorded | Per-ID reviewer decision tied to exact wording digest; changed text re-reviewed |
| Schemas and declarations | Closed schemas valid; semantic references valid; per-requirement states require an approved versioned declaration migration |
| Reproducible catalog | Generated bytes match committed sources; complete manifest and source revision are retrievable |
| Documentation consistent | Human normative view generated from that same canonical source; public status/links truthful |
| Change log and migration | Candidate-to-adopted changes and compatibility impacts recorded; historical pins retained |
| Governance approval | Actual authorized adoption record for exact release/content; no software-generated approval |
| Checksummed artifact | Source and final artifact digests verified; operator records exact publication bytes |
| Release and effective dates | Explicit dates approved; effective date no earlier than release date; no footer/artwork/generated time substituted |
| Publication/recovery plan | Approved transport/location, retained historical artifacts, operator procedure and rollback/withdrawal policy |

Schemas/digests provide integrity and structure, not governance authenticity. A green test suite cannot satisfy human review, adoption, approval or content adequacy gates. `oas:first:validate` validates a review package; it does not approve it. `releaseGates` explicitly reports blocked governance/publication stages and `assertAdoptable` refuses this package. The released-requirement guard requires a valid adopted release, active requirement, governance record bound to the exact catalog and an effective date, but does not validate approver identity or grant publication authority.

## Current version decision

Keep the only published pin OAS-1@0.0.0-public-review.1 byte-for-byte stable. Reserve 0.0.0-public-review.2 for a future reviewed draft but do not issue that release now. No 1.0.0-rc.1 or 1.0.0 is created. The version grammar permits prerelease spelling, but there is no adopted RC workflow/status and review gates have not passed; spelling an rc suffix would misrepresent readiness. A future explicit OAS decision must define RC semantics and any schema extension before using an RC label. Adoption of 1.0.0 always requires a separate recorded governance action.

## Subsequent change control

Never edit published normative text or checksummed artifacts in place. A clarification with unchanged meaning still needs reviewed changelog and a newly pinned publication if bytes change. If meaning or applicability changes, allocate new requirement IDs or an explicitly adopted requirement-version contract, publish a new standard release, link replacements reciprocally without cycles, and provide migration guidance. Existing foundation IDs identify immutable wording and originating release; do not repurpose them or infer cross-release applicability. Preserve deprecated/superseded rows and historical declaration pins. A newer status observation is separate from an original declaration; neither OAS nor Registry silently rewrites history.

## Authority and operational limits

OAS owns normative language and standards interoperability. Registry independently owns identity/registration/provenance/version/lifecycle/public records and may later reference adopted OAS IDs without redefining them. Trust Bureau independently assesses trust. SHS BOS remains operational/business infrastructure. No release decision creates Registry authorization, unrestricted execution, a trust score, assessment or certification. Rollback means stop new publication/use and publish an explicit correction/withdrawal decision while retaining historical artifacts; do not erase history.
