# OAS release candidate contract

An RC is an immutable reviewable standards candidate, not a final adopted standard. RC ≠ certification. RC ≠ Trust Bureau assessment. RC membership does not grant Registry registration, authorization or unrestricted execution. No RC exists merely because this document or its schema exists.

The explicit format is OAS-1@1.0.0-rc.N, with positive integer N, standard_version 1.0.0-rc.N and status release_candidate. schemas/oas/closure/rc.schema.json formalizes that separate contract without rewriting the published public-review.1 schema. Each RC carries a real candidate date; effective_date is null. Final 1.0.0 uses a different adoption/publication action and must never be inferred from the RC date or suffix.

Before issuance, every mandatory readiness gate must pass and a real founding maintainer must accept the exact source/scope/contracts and authorize issuance. Every included requirement must have an explicit content decision, stable identifier and exact finalized wording; deferred/rejected requirements cannot enter. Requirement IDs and domain IDs are unique, deterministically ordered, and must exactly match the accepted scope. No placeholder RC or empty mock membership is published to satisfy a test.

An RC records its exact full Git source revision, source manifest checksum, requirement-content checksum and artifact checksum, with its exact scope checksum, governance decision reference, changelog reference and declaration schema ID. The predecessor is the preserved public-review.1 artifact with relationship derived_from_historical_public_review; derivation is not an adopted supersession event. Verify that the source revision contains the accepted bytes. SHA-256 verifies byte integrity, not the identity, authority or independent consensus of the publisher.

Once issued, membership, normative wording, dates and bytes for that RC never change. Corrections require the next explicit RC number, a new source revision/checksum, an itemized changelog and a new reviewed issuance decision. Editorial clarifications still change bytes and therefore require another RC. A material normative meaning/applicability change uses a new requirement ID or an explicitly adopted requirement-version contract and supersession/migration relationship; do not reuse an immutable ID for a different obligation. Historical RCs and declarations remain retrievable.

Consumers may rely on the pinned RC's exact member IDs, text, scope, schema compatibility and digests for RC validation/testing only. They must not infer that an RC is current from a floating latest label, treat it as final adopted normative authority, infer implementation satisfaction or certification, or silently upgrade an older declaration. Currentness requires comparison against explicit authoritative publication records; no such new RC record is created in this branch.

After RC validation, record issue outcomes, any changed wording/membership, migration guidance and a separate final-adoption decision with release/effective dates and authorized publication of exact final bytes. A final version never overwrites the RC. The first final release is not authorized by the present task. RC publication, hosting/deployment and final publication are distinguishable from committing review material.
