# CivicSure Report Generation Capability Audit

## 1. Executive Result

**Audit status:** complete, read-only.

The repository has a canonical Reporting authority that can compose five GPA report types from bounded, organization/tenant-scoped canonical GPA projections and persist report artifact metadata. The current GPA report experience is operational JSON generation with browser-created JSON download. It is not an executive-grade printed-report system.

The existing architecture should be extended, not replaced. The most important missing capability is a server-owned, immutable rendered-file layer bound to an exact `report_artifact` and version. PDF and HTML renderers found elsewhere are renderer-only or legacy/demo paths and are not currently safe to promote as CivicSure artifact authority.

**Recommended next step:** report system design beginning with a bounded artifact/template/rendering foundation. No runtime changes were made in this audit.

## 3. Canonical Reporting Authority

The canonical authority is the existing Reporting domain under `apps/shs-api/src/domain/reporting/`, centered on:

- `ReportArtifactService` and `ReportArtifactRepo` for scoped artifact metadata;
- reporting routes under `/reporting` for artifacts, drafts, exports, distribution, and public governance;
- `GovernmentAssurancePhase8BService.generateReport()` for the GPA composition adapter;
- `PilotReportingService` for server-side GPA dashboard and readiness projections;
- `report_artifacts` migration 012 for persisted artifact metadata;
- separate Public Disclosure, snapshot, publication, and authorization services for public output.

This is one Reporting authority. The GPA adapter does not create a second report database or report authority.

## 4. Reporting Architecture Map

```text
GPA Reports UI
  -> government-assurance-client.generateGovernmentAssuranceReport()
  -> POST /government-assurance/reports/generate
  -> GovernmentAssurancePhase8BService.generateReport()
  -> PilotReportingService.dashboard() + bounded GPA table projections
  -> canonical GPA tables/services
  -> ReportArtifactService.createArtifact()
  -> report_artifacts metadata row + audit event
  -> response contains report payload plus artifact metadata
  -> browser currently creates a JSON Blob for download
```

The separate Reporting routes support artifact reads/lists, draft/revision workflows, export-history records, distribution authorization, and Public Disclosure governance. The GPA generation route currently returns the composed report in the response; it does not bind rendered bytes to the artifact.

## 6. Supported Report Types

The GPA adapter accepts exactly:

1. `EXECUTIVE_ASSURANCE`
2. `PROGRAM_ASSURANCE`
3. `PROVIDER_ASSURANCE`
4. `FUNDING_LINEAGE`
5. `AUDIT_PACKET`

All currently use the same bounded composition pattern, with subject filtering for Program, Provider, Funding, and Audit. The report type controls classification and filtering, but there is not yet a separate presentation template or persisted content model for each type.

## 7. Executive Assurance Report

**Builder:** `GovernmentAssurancePhase8BService.generateReport()` plus `PilotReportingService.dashboard()`.

**Current coverage:** PARTIAL. The payload includes dashboard summary values for claims, verified claims, providers, programs, accepted Truth Facts, open Findings, Reconciliation cases, overdue Corrective Actions, audits, source systems, stale/degraded sources, monitoring plans, awarded funding, obligated funding, and verified expenditure. It also includes bounded claims, metrics, accepted Truth, funding, Findings, Reconciliation, audit, and source rows.

The current payload does not provide a designed executive narrative, a report-period contract, a formal Decisions Required section, methodology, appendices, page layout, or printable artifact.

## 8. Program Assurance Report

**Current coverage:** PARTIAL. Program-scoped funding is filtered by `program_reference`, while the common bounded context supplies claims, metrics, Truth, Findings, Reconciliation, audits, and sources. Provider/service/outcome presentation, program-specific assurance sections, methodology, and rendered layout are not separately modeled.

## 9. Provider Assurance Report

**Current coverage:** PARTIAL. Funding is filtered by `provider_organization_reference` and common canonical context is included. The provider integrity projection is not transformed into a dedicated provider report schema or print template. Restricted Investigation data is not part of the GPA report context, which is an important preservation property.

## 10. Funding Lineage Report

**Current coverage:** PARTIAL. Funding is filtered by funding reference and the funding rows are sourced from GPA funding references. A formal forward/reverse lineage appendix, amount semantics, source provenance presentation, and rendered lineage layout are not present in the report artifact.

## 11. Audit Packet

**Current coverage:** PARTIAL. Audit engagements are filtered by engagement ID and included in the bounded context. There is no dedicated packet renderer or persisted packet file containing workpapers, samples, sample results, Findings, Decisions, and references. The selected classification is `RESTRICTED_EXTERNAL`.

## 12. Official Number Lineage

The GPA report builder obtains official dashboard amounts through `PilotReportingService`, including SQL aggregation over `gpa_funding_references` for AWARD, OBLIGATION, and VERIFIED EXPENDITURE. Other report facts come from bounded organization/tenant-scoped GPA table reads. React does not calculate official GPA numbers; it displays the server response and serializes that response for the current JSON download.

Current lineage is therefore:

```text
canonical GPA tables/services
  -> PilotReportingService / Phase8B bounded context
  -> report response canonicalFacts + canonicalReferences
  -> ReportArtifactService manifest metadata
```

No evidence was found that AI creates official report numbers. The AI service is advisory and is not called by `generateReport()` unless caller-provided `aiInvolvement` metadata is supplied. The current report adapter does not independently invoke a model.

**Important limitation:** the manifest records report/reference identifiers and versions, not a complete immutable numeric snapshot or calculation-version record.

## 13. Reproducibility

**Assessment: PARTIALLY REPRODUCIBLE.** The system records report type/version, artifact composition version, organization/tenant, actor, subject reference in the response, generation time, and canonical input manifest. The same scope can be queried again, but exact reproduction is not guaranteed because the artifact does not persist the composed payload, source snapshots, metric-definition versions, calculation version, template version, or render bytes.

The generation idempotency key prevents some duplicate creation paths, but default GPA keys include the current timestamp, so ordinary generation is not a deterministic replay contract.

## 14. Snapshot Semantics

The system is a mixture:

- `report_artifacts` is durable metadata and a canonical-input reference, not a full immutable rendered snapshot;
- the GPA report response is a generated live composition at request time;
- Public Disclosure has separate immutable public-safe snapshot tables and publication controls.

Immutable public snapshots exist for the governed public path. Immutable internal CivicSure report bytes do not currently exist.

## 16. PDF Capability

Repository-wide PDF-related capability exists, but no current candidate is a canonical CivicSure GPA renderer:

- `services/shf-report-engine/src/render.js` uses Playwright to render fixture HTML to local PDF outputs;
- Agent Fabric institutional/funder/report builders and `pdf_report.py` can produce in-memory or local PDF bytes;
- `pdf-lib` is an API development dependency and `pdf-parse`/`mammoth` support source ingestion/inspection, not GPA report output;
- the canonical report file authority contract classifies these as `RENDERER_ONLY` because they lack exact artifact/version binding, durable scoped storage, and canonical file ownership.

No evidence of GPA-specific PDF headers/footers, page numbering, classification marks, table pagination, embedded CivicSure branding, or accessible PDF output was found.

## 17. Print Capability

Generic application pages contain `window.print` and `@media print` rules, including resume, sales, funding-plan, and other unrelated surfaces. No GPA report print route or GPA-specific print stylesheet was found. Browser print is therefore not an accepted CivicSure report path.

## 18. Template System

The GPA report adapter constructs a plain JavaScript object directly in `phase8b-service.ts`. No GPA report template registry, JSON schema, HTML/JSX report template, template version, or separate data-payload/template/render stages currently exist.

The separate `ReportDraftService` stores draft configuration and revisions and is reusable for future report preparation, but its current generic draft model is not a CivicSure rendered-report template system.

## 19. Visual / Branding Capability

The current GPA report UI is operational/technical rather than executive-ready. It displays a report-type selector, optional subject reference, generated artifact metadata, canonical-reference count, and a bounded JSON download. It does not render a CivicSure cover, structured sections, headers/footers, tables, charts, methodology, appendices, page numbers, or classification banners.

The current customer-facing shell is being separately evolved toward CivicSure, but report output itself has no report-specific CivicSure branding contract.

## 20. County Branding Capability

**PARTIAL.** The report scope contains organization and tenant IDs and can be extended with jurisdiction/department configuration without changing GPA authority. There is no approved county display-name, seal/logo reference, contact block, or branding policy in the current report composition. Any future branding must use server-authorized configuration and references, never client-supplied arbitrary images or names as official identity.

## 21. Preview Capability

**PARTIAL.** `REPORTS_PREVIEW` and `/reporting/drafts` provide generic draft/preview infrastructure. The GPA UI currently generates the report and displays metadata; it does not preview a formatted report. There is no GPA HTML preview, print preview, page-break validation, or rendered-artifact preview route.

## 22. Report History

**PARTIAL.** `/reporting/artifacts` and `/reporting/artifacts/:artifactId` support scoped metadata list/read, and `ReportDraftService` supports draft revisions. The GPA Reports UI does not expose artifact history, prior report retrieval, supersession, or version comparison. `/reporting/exports` uses an in-memory process-local history store and is not durable artifact history.

## 23. Approval Workflow

Generic report drafts have a `draft` lifecycle and revisions. Public Disclosure has strong separate policy, signoff, eligibility, snapshot, release approval, and publication authorities. There is no general internal CivicSure report lifecycle of DRAFT → REVIEW → APPROVED → RELEASED for private artifacts. Future approval should reuse existing Decision/audit/Public Disclosure controls where applicable rather than add a report-local decision authority.

## 24. AI Narrative

The GPA AI endpoint returns separated canonical facts, analysis, recommendation, canonical references, security result, and provenance. `generateReport()` does not call AI itself; it accepts optional `aiInvolvement` metadata. Therefore there is no current governed AI narrative pipeline inside generated reports.

If narrative is added later, canonical numeric payload generation must precede model invocation, the narrative must be labeled advisory, model/provider/session metadata must be retained, and server validation must reject or quarantine factual contradictions.

## 25. Classification

The artifact authority supports `INTERNAL`, `RESTRICTED_EXTERNAL`, and `PUBLIC`. GPA assigns `INTERNAL` to all report types except `AUDIT_PACKET`, which is `RESTRICTED_EXTERNAL`. The broader Public Disclosure authority has policy, signoff, eligibility, snapshot, release, and publication controls.

The current artifact metadata does not cover the full requested `CONFIDENTIAL` and `HIGHLY_RESTRICTED` taxonomy, and classification is not visibly printed on every rendered page because no rendered page exists. Classification is enforced for API artifact scope and public workflows, but the report file/print layer remains missing.

## 26. Public Disclosure Boundary

The boundary is preserved. Internal artifact generation does not itself publish data. Public output requires separate public eligibility, disclosure decision, policy/signoff, immutable public snapshot, release approval, and publication services. Accepted Truth is not equivalent to public approval. The public summary route filters accepted Truth to `PUBLIC_APPROVED` records.

## 27. Authorization

Relevant permissions include:

- `reports.view` for artifact/draft/history reads;
- `reports.preview` for draft creation and edits;
- `reports.export` for GPA generation, artifact creation, and export records;
- separate permissions for public disclosure, public snapshot, publication, distribution recipients, and release authorization.

Artifact reads are scoped by server-derived tenant and organization. The main GPA generation route is permission guarded, and the Phase 8 browser tests cover same-scope generation and wrong-organization denial. Future rendered files must re-check authorization at retrieval time, reject client-provided storage paths, and avoid public links for restricted artifacts.

## 28. Report Storage

Current GPA report storage is database metadata in `report_artifacts`, including canonical manifest and lifecycle metadata. The composed report payload is returned to the client but is not stored in `report_artifacts`. No durable object/file storage, MIME type, byte length, file reference, exact-byte hash, retention policy, or immutable-file retrieval path exists for GPA reports.

The repository’s canonical report file authority contract explicitly records this as `SERVER_RENDERER_EXISTS_BUT_DURABLE_STORAGE_MISSING`.

## 29. Large Report / Pagination

The GPA server context bounds each source table query to 50 rows. Canonical references are capped at 40. This is pilot-safe but means large reports are truncated rather than paginated or appendix-complete. There is no page-layout engine, streaming render, large-table pagination contract, or memory test for 10/50-page reports.

## 30. Chart Capability

The root application contains chart/visualization libraries and unrelated chart-like UI assets, but no GPA report chart adapter. No report-specific accessible chart renderer, server-side chart snapshot, or canonical chart-to-PDF path was found. Future charts should be limited to decision-useful canonical series and provide tabular/text alternatives.

## 31. Evidence / Lineage Appendix

**Feasible but not implemented.** GPA responses already expose canonical references for Claim, MetricResult, TruthFact, Finding, and Funding. Funding and Metric/Truth services also expose lineage endpoints. A future appendix can be generated from those references plus source/provenance and methodology metadata without copying raw Evidence payloads into the file authority.

## 32. Signature / Approval Evidence

Public Disclosure and publication authorities have explicit approval/signoff records. Report draft creation/update has audit events. No general private report prepared/reviewed/approved signature block or e-signature artifact is attached to GPA report output. Future signatures should reference existing Decision/approval authorities and remain audit events, not become a new report authority.

## 33. Export Security

Current protections include permission guards, organization/tenant-scoped artifact queries, server-derived artifact identity, classification validation, audit events, and separate public governance. Current risks/gaps are:

- browser JSON download is local presentation output, not durable controlled bytes;
- no durable download endpoint with retrieval-time authorization exists for GPA output;
- no artifact hash is available because no bytes are stored;
- no filename policy beyond lower-case report type plus artifact ID;
- no cache-control, revocation, retention, or link-expiration contract is visible for GPA downloads;
- process-local export history is not durable and is not a source of artifact authority.

## 34. File Naming

Current GPA browser naming is approximately `<reporttype>-<artifact_id>.json`. It is functional but not human-oriented and contains no jurisdiction, period, report version, or classification marker. Recommended future convention:

`CivicSure_<Jurisdiction>_<Report-Type>_<Period>_v<Report-Version>.<format>`

The server should own the safe filename and prevent sensitive subject data from leaking through filenames.

## 36. Executive Print Requirements

The future CivicSure Executive Assurance PDF should be a server-rendered, immutable artifact with:

1. Cover: CivicSure, agency/county, report title, period, generation date, classification.
2. Executive Summary with explicit canonical-fact versus advisory narrative distinction.
3. Funding Assurance: awarded, obligated, paid/reported, verified expenditure with source references.
4. Program Assurance and Provider Assurance sections.
5. Verified Outcomes with Metric Definition/version, Verification level, Claim/Evidence references.
6. Findings and Corrective Actions, including open material issues.
7. Audit, Data Quality, Reconciliation, and Source Health.
8. Decisions Required, clearly distinguished from recommendations.
9. Evidence & Methodology appendix with canonical IDs, lineage, data-as-of, and calculation versions.
10. Headers/footers, page numbers, classification marking, accessible tables, deterministic page breaks, and exact-byte hash metadata.

## 37. Frontend Report Experience Requirements

The future workflow should be:

`Reports -> choose type -> choose authorized scope -> choose period -> validate readiness -> preview -> generate -> review metadata -> approve where required -> retrieve/download -> history`

Current support is: choose type, optional subject, generate, display limited metadata, and local JSON download. Missing are period validation, formatted preview, readiness validation, review/approval state, durable retrieval, history, and controlled print/download.

## 40. Recommended Report Architecture

```text
Canonical GPA authorities
  -> typed server-side Reporting projection
  -> immutable canonical report payload/snapshot
  -> versioned CivicSure template
  -> server-side render adapter
  -> PDF / HTML preview / bounded JSON or CSV
  -> durable immutable report file record
  -> hash, metadata, retention, scoped retrieval
  -> review/approval/distribution/Public Disclosure as separate governed steps
```

The file record must reference exact `artifact_id` and `artifact_version`, exact template/render version, server-derived scope, MIME type, byte length, hash, and authorized storage reference. Raw Truth, Evidence, participant, and restricted source payloads should not be copied into file authority.

## 41. Recommended Implementation Waves

### Report R1 — Artifact and Template Foundation

Define typed GPA report payloads, report period/data-as-of semantics, template versioning, immutable internal snapshot semantics, durable file ownership, exact-byte hash, scoped retrieval, and metadata contract. Preserve migration 105 unless a reviewed schema change is required.

### Report R2 — Executive Assurance PDF

Implement the server-side CivicSure executive template, accessible tables, classification markings, headers/footers, page numbering, methodology/lineage appendix, preview, and deterministic PDF regression fixtures.

### Report R3 — Program, Provider, and Funding Reports

Add typed scoped templates, forward/reverse funding lineage presentation, provider/program assurance sections, and controlled JSON/CSV where operationally justified.

### Report R4 — Audit Packet

Compose workpapers, sampling, results, Findings, Decisions, Evidence references, and methodology into a restricted packet with explicit authorization.

### Report R5 — History, Approval, and Distribution

Expose durable artifact history, review/approval references, supersession, retention, revocation, and distribution adapters. Keep Public Disclosure separate and require its existing gates.
