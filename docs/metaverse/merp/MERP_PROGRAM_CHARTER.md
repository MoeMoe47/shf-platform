# MERP Program Charter

MERP is the Metaverse Experience Reconstruction Program for the existing Silicon Heartland Metaverse. It is an independent visual and experience reconstruction program that improves the metaverse shell phase by phase, with mandatory owner visual review between phases.

## Purpose

MERP owns the visual experience layer of the metaverse:

- clean production backgrounds
- visual scene calibration
- collapsible sidebar
- contextual right drawer
- compact HUD
- road tracing
- perspective-scaled traffic
- buses
- freeway light streaks
- slow clouds
- sparse birds
- wind turbine motion
- time-of-day presentation
- responsive visual polish
- accessibility of the metaverse experience shell

MERP does not own or replace canonical authority systems:

- Identity authority
- Organization authority
- Role authority
- Entitlement authority
- Curriculum authority
- Career authority
- Civic authority
- Opportunity authority
- Market authority
- Treasury authority
- Evidence authority
- Credential authority
- Truth Spine
- Reporting authority

Those systems remain canonical. MERP may present their state only through existing authorized frontend projections and may not move, redefine, persist, or fabricate authority.

## Locked Visual Model

The final metaverse experience follows this model:

CITY CANVAS = WORLD
LEFT SIDEBAR = GLOBAL SYSTEMS
RIGHT DRAWER = CONTEXT
MOTION = SUBTLE ENVIRONMENTAL LIFE

The city remains the visual hero. The target shell is:

- slim collapsible left sidebar
- open city canvas
- compact top-center Next Action
- one closable right contextual drawer
- small location markers
- compact bottom contextual navigation
- small lower-right mini-map/camera controls
- no permanent dashboard clutter
- no multiple giant panels covering the scene

Everything added to upgrade the metaverse must be reachable through either the collapsible left sidebar or the temporary closable right contextual drawer. MERP must not add permanent large floating panels.

## Phase And Review Rule

MERP advances only one phase at a time. Every phase must end with a visual review artifact and owner acceptance before the next phase begins.

No phase may advance on technical completion alone. Visual acceptance is required.

## Visual Approval Requirement

Any change to production backgrounds, city shell layout, persistent overlays, motion density, vehicle rendering, time-of-day presentation, or responsive metaverse shell behavior requires visual review before it can be considered complete.

Screenshots are required for visual phases unless runtime capture is blocked. If capture is blocked, the phase report must document the blocker.

## Authority Boundary

MERP may:

- read canonical projected state already exposed to the metaverse UI
- improve presentation of city, district, facility, and shell surfaces
- document current asset and motion behavior
- add presentation-only visual helpers when explicitly scoped

MERP may not:

- migrate authority
- modify backend business logic
- change eligibility, unlock, evidence, credential, reporting, treasury, market, civic, curriculum, career, identity, role, or organization semantics
- make decorative motion grant access or imply system truth
- replace canonical registries with visual-only registries

## No Phase Advancement Without Acceptance

MERP-0 is audit and documentation only. MERP-1 may not begin until the owner visually accepts the MERP-0 baseline and the recommended MERP-1 starting target.
