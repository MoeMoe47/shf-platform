# Final 1.0 disposition of the eight HOLD requirements

Repository scope and contract closure under the user task directive. FOUNDING GOVERNANCE is not external consensus. This is not an adopted standard or issued RC; real exact-snapshot founding acceptance is still missing.

| ID | Disposition | Reason / first-release necessity | Future issue category |
| --- | --- | --- | --- |
| OAS-1-REQ-0002 | MOVE TO APPROVE | A source artifact reference identifies the declared system version directly or through an origin record that identifies that version. A composite/hosted system can reference a version-specific manifest or origin record; a generic homepage that cannot identify the described version does not meet the existing identification obligation. | Included in the information baseline |
| OAS-1-REQ-0007 | MOVE TO APPROVE | Resources means the declared version's required execution resources and external tool/system dependencies within the stated operating scope, not an unbounded supply-chain census. The obligation concerns used dependencies; merely accessible but unused tools remain covered by capability/permission descriptions. Dynamic dependencies can be identified by a version-specific dependency/selector manifest. | Included in the information baseline |
| OAS-1-REQ-0010 | MOVE TO APPROVE | The prohibition set is attributed to the provider's applicable policy for this version/scope; OAS does not invent a universal legal or safety blacklist. An explicit empty list describes the provider's policy claim and is not a safety finding. A missing or unknown prohibition set is not a satisfied declaration. This is safety-constraint disclosure, distinct from the general operating exclusions in 0004. | Included in the information baseline |
| OAS-1-REQ-0011 | REMAIN DEFERRED FOR POST-1.0 | Control-to-prohibition effectiveness and partial/unavailable-control disclosure needs a separate control model. Constraint disclosure is already covered by 0010; actual prevention/effectiveness is not necessary to an information baseline. | operational control coverage and effectiveness |
| OAS-1-REQ-0012 | MOVE TO APPROVE | The word or is disjunctive: this obligation documents the authorized human role and interfaces for the interventions actually documented. It does not assert that every system supports all three interventions. Unsupported stop/override capability must not be advertised as present. Human oversight can be documented through its actual inspection/control interface; latency/effectiveness is outside this baseline. | Included in the information baseline |
| OAS-1-REQ-0013 | REMAIN DEFERRED FOR POST-1.0 | Runtime escalation trigger/destination applicability is a later operational-control issue. The first baseline already records human responsibility/intervention interfaces through 0012; it does not promise response handling. | operational escalation applicability and response |
| OAS-1-REQ-0015 | REMAIN DEFERRED FOR POST-1.0 | Requirement-to-evidence references are enforced by the declaration contract. A separate normative evidence-typing obligation is deferred until evidence sufficiency/access/retention semantics are governed; 0014 supplies the initial plan baseline. | evidence typing, sufficiency and retention |
| OAS-1-REQ-0016 | MOVE TO APPROVE | The lifecycle state is explicitly provider-defined. Its meaning is inspected in the provider's referenced description/vocabulary, not mapped to Registry lifecycle by matching a label. A bare value without an interpretable provider description cannot substantiate the claimed state. Version/state here describe the subject, not OAS release status. | Included in the information baseline |

All IDs remain reserved. No deferred/rejected member enters the 14-item scope. Deferral does not erase the original concept or assert that runtime controls/evidence sufficiency are unnecessary in future standards.
