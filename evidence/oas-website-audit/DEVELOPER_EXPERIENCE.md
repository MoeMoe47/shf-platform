# Developer experience

A developer can currently learn broad OAS intent and see eight domain labels and an informative risk graphic. They cannot use the public website to obtain the current final release, read the fourteen exact requirements, consume JSON/catalog/schema, inspect source hashes, pin a release or understand currentness/declaration receipts. Read Full Specification and Machine-Readable Schema are disabled; Implementation and Developer Resources are planned; Governance leads to the footer. No API/consumer/backend integration exists in the website.

Required launch information surface (can extend /oas-1.html): exact OAS-1@1.0.0/date/status; canonical requirement IDs/text grouped under all eight domain IDs; exact human artifact/catalog/currentness access; checksums/source revision; stable pinning examples; 1.1.0 schema/declaration shape; provider attribution/scope/evidence references; NOT_EVALUATED explanation; empty profiles; distinction between structural reference verification, behavioral evaluation, certification and Registry registration. Examples must be explicitly synthetic and never a real declaration or certification. Provide version/currentness history without floating latest dependencies.

No requirement to build an SDK, API authentication, interactive certifier or Registry workflow in OAS. Optional future guides, FAQ and use cases should follow actual artifact access. PDF is optional; the already-frozen human Markdown suffices for initial authoritative reading if clearly accessible. Do not create a second normative catalog or alter frozen fields to fit a website design.
